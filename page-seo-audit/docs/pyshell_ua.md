# Аудит SEO сторінки

Повний on-page SEO-аудит **одного URL**: статус відповіді, мета-теги та
індексованість, структура заголовків, `alt`-текст зображень, Open Graph /
Twitter Card, hreflang, структуровані дані (JSON-LD, microdata, RDFa),
кількість слів і mixed content — один запит, один прохід парсингу, звіт
за секунди. Без краулінгу.

Це одноразовий аналог пари [Site Crawler](../../site-crawler) +
[SEO Checks](../../seo-checks): тій парі потрібен повний краул, щоб сказати
щось корисне (дублікати, залежність від редіректів та індексованість —
це все порівняння *між* сторінками); цей скрипт відповідає на питання
«чи ця окрема сторінка нормальна?» за одним URL. HTTP security-заголовки
мають власний скрипт ([Security Headers](../../security-headers)) і тут
навмисно **не** перевіряються вдруге.

---

## Перед запуском

1. Натисніть **Prepare Env** — встановить `requests` і `lxml`.
2. **URL** — сторінка для аудиту, зі схемою (`https://…`).

---

## Поля

### Запит

- **URL** — сторінка для аудиту. Введення без схеми автоматично
  отримає префікс `https://`.
- **Переходити за редіректами** (увімкнено за замовчуванням) — аудит
  сторінки, на якій URL нарешті опиняється. Ланцюжок редіректів
  показується так чи інакше, тож ви завжди знаєте, чи аудитована
  сторінка — це URL, який ви задали.
- **Таймаут (с)** — на один запит; кожен перехід редіректу має свій
  бюджет.
- **User-Agent** — за замовчуванням ідентифікує скрипт як PyShell-аудит.
  Деякі WAF тихо дропають голий `python-requests`, що виглядає як
  таймаут. Повністю порожнє значення повертається до того самого
  значення за замовчуванням замість порожнього заголовка.
- **Не перевіряти TLS** — для внутрішніх/staging-хостів із
  самопідписаними сертифікатами. Поширюється також на опційну перевірку
  посилань і запит robots.txt нижче — щоб посилання на staging не
  провалювалося через той самий сертифікат, який дозволено пропустити
  для самої сторінки.

### Перевірки

- **Поріг «тонкого контенту» (слів)** — Content отримує info-фіндинг
  нижче цієї кількості. 300 — загальна евристика; зменшіть для сайту з
  переважно короткими довідковими сторінками, збільшіть для лонгрідів.
- **Перевіряти robots.txt** — один додатковий запит на той самий хост,
  що додає рівень «дозволено на рівні краулінгу» до того самого
  вердикту індексованості, що й `<meta name=robots>` та `X-Robots-Tag`.
  Сторінка може не мати жодного `noindex` і все одно бути недоступною
  краулерам, бо robots.txt блокує шлях.
- **Перевіряти посилання на сторінці** — **вимкнено за замовчуванням.**
  Це єдина опція, що надсилає запити за межі самої сторінки: кожне
  унікальне посилання на сторінці отримує один `HEAD`-запит із fallback
  на `GET`, де HEAD не дозволено (або відхилено з 4xx, відмінним від
  404/410). Посилання в футері, повторене 50 разів — все одно один
  запит. У тому ж проході перевіряється й **ціль canonical** — canonical
  на мертвий чи редіректний URL консолідує сторінку в ніщо, чого
  перевірки наявності тега ніколи не бачили.
  - **Які посилання перевіряти** — усі, лише внутрішні, або лише
    зовнішні.
  - **Макс. посилань для перевірки** — жорстко обмежує кількість
    запитів (0 = без обмеження); мертвий CDN за сотнями посилань більше
    не означає сотні фіндингів теж — понад 20 мертвих посилань решта
    підсумовується одним рядком.
  - **Конкурентність / таймаут перевірки посилань** — окремі ручки лише
    для цього проходу.
- **Категорії, які прибрати зі звіту** — приховати категорію повністю,
  напр. Social на внутрішньому адмін-інструменті, який ніколи не
  генеруватиме прев'ю для шерингу.

### Вивід

- **Провалювати запуск при** — `none` (за замовчуванням) завжди завершує
  успішно, що б не знайшлося; `warn` або `fail` робить сам запуск
  невдалим (код виходу 2), щойно з'являється фіндинг такої серйозності
  чи гірше. Підключіть це до гейта в пайплайні замість парсингу тексту
  зі звіту.

## Що перевіряється

| Категорія | Перевірки |
|---|---|
| Response | сам статус відповіді: 2xx = pass, тіло нерозгорнутого редіректу = warn, 4xx/5xx = fail (усі фіндинги нижче описують сторінку помилки, не реальний контент); схема фінального URL — https = pass, сторінка, що відповідає по чистому http без редіректу на https = warn (нерозгорнутий 3xx по http мовчить: він міг би ще редіректити туди); тут же — довжина ланцюжка редіректів, редірект без `Location`, обрізане тіло |
| Meta | `<title>` (відсутній = fail, дублікат = warn, довжина поза ~50–60 = info), meta description (відсутнє = warn, дублікат = warn, ~120–158 = info), **canonical** — дублікати тегів = warn, нерозв'язний = warn, self-referencing = pass, вказує на інший домен = warn («сторінка просить виключити себе з індексу»), вказує на інший URL того ж хосту = info, **індексованість** — `noindex` (чи його аналог `none`, зокрема бот-специфічні мета як `googlebot`) з meta robots, `X-Robots-Tag` або robots.txt, із зазначенням усіх джерел (warn), viewport (відсутній = warn), charset (не задекларовано = warn — саме та вада, через яку раніше псувалась кирилиця у fetch-шарі скрипта), favicon (відсутній = info), `<html lang>` (відсутній = info), застарілий `<meta name=keywords>` (info) |
| Headings | нуль `h1` = fail; кілька `h1` = warn; порожній текст заголовка = warn; заголовок перед першим `h1` = info; пропуск рівня вниз (`h1` → `h3`) = info; `h1` довший за ~70 символів або ідентичний `<title>` = info |
| Images | зображення без атрибута `alt` — один агрегований warn («N з M»). `alt=""` (декоративне) — коректне позначення, яке ніколи не позначається як проблема. Понад наявність: `alt` із самих пробілів (warn — не те саме, що `alt=""`), `alt` довший за 125 символів (info), `alt`, що не каже нічого понад ім'я файлу (info, напр. `alt="photo.jpg"`), відсутні `width`/`height` (info — найдешевший фікс зсуву макета), ліниво завантажене перше зображення (info — ймовірно затримує власний LCP сторінки) |
| Social | Open Graph: усі відсутні = warn; `og:image` відсутній = warn; *відносний* `og:image` **або `twitter:image`** = warn (більшість краулерів вимагають абсолютний URL); `og:url`, що розходиться з canonical = info; порожній `og:title`/`og:description` = warn. Twitter: відсутній `twitter:card` — лише info, коли є Open Graph (платформи fallback-ать на OG), warn коли немає обох, warn коли значення не з переліку допустимих типів картки, і warn коли `summary_large_image` без `twitter:image` |
| Hreflang | мовчить на сторінці без жодного `hreflang`-альтернативу. За наявності: невалідний код мови = warn, той самий код двічі = warn, невабсолютна ціль = warn, жоден запис не вказує на цю ж сторінку = warn («набір без self-reference ігнорується повністю»), відсутній `x-default` = info, self-referencing-запис, що заявляє іншу мову, ніж `<html lang>` = warn (регіональні варіанти тієї ж мови — `en` проти `en-GB` — це згода; `x-default` ніколи не конфліктує) |
| Structured Data | кожен `<script type="application/ld+json">` парситься; битий JSON = fail; парситься, але без `@context` = fail (ігнорується так само мовчки, як і битий JSON); є `@context`, немає `@type` = warn; валідні блоки звітують свої `@type` (об'єкт, `@graph`, масив). Читаються також microdata (`itemtype`) і RDFa (`typeof`), тож сторінка лише з ними не звітується як «немає структурованих даних». Нуль будь-яких — info, покращення, а не базова вимога |
| Content | кількість слів нижче порогу вище = info; рахується лише з тексту `<body>`, з коректним пробілом між текстом, розбитим по блокових елементах; співвідношення тексту до розмітки нижче 5% = info (зазвичай клієнтський рендер без вмісту); відсутній `<main>`/`<article>` = info; кількість `rel=nofollow`/`sponsored`/`ugc` посилань = info; анкори, які краулер не може пройти (`href="#"`, `#фрагмент`, `javascript:…`) = warn — і вони більше не рахуються внутрішніми посиланнями, як це раніше робило розв'язання фрагментів у `urljoin()` |
| Mixed Content | на https-сторінці: будь-який субресурс — `img`, `script`, `iframe`, `video`, `audio`, `source`, `embed`, `track`, `<link>` стилів/іконки/маніфесту, елемент `srcset`, дія форми — завантажений по голому `http://` = warn. `rel=alternate` (RSS) і `rel=preconnect` ніколи не є субресурсами і ніколи не позначаються |
| Links | вимкнено, якщо не ввімкнено **Перевіряти посилання**: не-2xx = один fail на кожне мертве посилання (з обмеженням і підсумком), досяжне лише через редірект = info; ціль canonical перевіряється в тому ж проході — недосяжна/помилкова = fail, редіректна = info, жива = pass |

**Жодного єдиного балу.** Незалежні сім'ї перевірок роблять
обґрунтований зважений бал таким, що його важко відкалібрувати «на
папері», тож результат — таблиця статусів по категоріях
(pass/warn/fail/info в кожному рядку) плюс файндинги, найгірші перші —
«Images: warn, Structured Data: pass» корисніше за абстрактні 74/100.

## Результат

- **Вкладка Results** — markdown-звіт: статус відповіді та зведення
  редіректів, таблиця статусів по категоріях, потім усі файндинги
  (Категорія / Статус / Деталь / Виправлення), найвища серйозність
  першою.
- **Артефакти** — `page_facts.json` (усі сирові факти — докази),
  `findings.json` (машиночитний: кожен фіндинг має стабільний `code` на
  додачу до текстового `detail`, плюс зведення `counts` і
  `category_status` на верхньому рівні — CI-правила прив'язуються до
  `code`, а не до формулювання, яке можна переписати пізніше), `report.md`.

## Код виходу

- `0` — сторінку отримано і проаудитовано, і нічого не перетнуло поріг
  **Провалювати запуск при**. Сторінка, що провалила всі перевірки —
  за замовчуванням все одно успішний аудит.
- `1` — немає придатної відповіді: таймаут, connection refused, DNS,
  ланцюжок редіректів, що ніколи не розв'язується, не-HTML відповідь
  (JSON, зображення, PDF — там нема on-page SEO для аудиту), або тіло,
  що не парситься як HTML.
- `2` — аудит завершився повністю, але фіндинг на рівні **Провалювати
  запуск при** чи гірше був присутній.

Червоний рядок у History від коду `1` означає «запит не долетів», а не
«сторінка отримала низьку оцінку» — саме для цієї різниці існує код `2`.
