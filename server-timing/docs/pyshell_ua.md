# Server Timing

Вимірює час відповіді сервера серією запитів і показує перцентилі, а не
середнє. Нічого не змінює на цілі, тільки читає.

## Перед запуском

- **Cache-bust** — додає `?_cb=<uuid>` і б'є повз CDN/сторінковий кеш прямо
  в застосунок. Без нього міряється кешована віддача — це інше число.
- **Count / Delay** — типові 20 запитів з паузою 0.2с обрані, щоб серія не
  виглядала як атака на цілі з базовим rate-limiting.
- **Reuse** — вимірює keep-alive; з ним DNS/TCP/TLS будуть нулями з другого
  запиту, і фазова розбивка стає непоказовою для перших трьох фаз.

## Результат

Таблиця фаз (p50/p95/max) і графік у вкладці Results; JSON/CSV/Prometheus —
у вкладці артефактів, якщо обрано відповідний формат.

## Як читати результат

Кожен запит розбивається на фази; таблиця показує p50/p95/max/mean по кожній
фазі, у мілісекундах.

| Фаза | Що вимірює |
|---|---|
| `dns` | Перетворення імені хоста в IP-адресу. Зазвичай близько до нуля — ОС кешує DNS-запити, і прогрівочні запити теж гріють цей кеш. |
| `connect` | TCP-хендшейк — один мережевий раунд-трип до сервера. З другим запитом і далі — нуль, якщо увімкнено **Reuse**. |
| `tls` | TLS-хендшейк, лише для HTTPS — для `http://` рядка немає. |
| `server` | Час роботи застосунку: від «запит надіслано» до «заголовки відповіді отримано», мінус `dns`/`connect`/`tls`. Містить приблизно один мережевий раунд-трип (запит летить туди, заголовки — назад), тож це справді *чистий* час сервера лише на localhost. |
| `transfer` | Читання тіла відповіді після заголовків. Росте з розміром тіла й падає зі швидкістю каналу; `--gzip` його скорочує, але це навмисно інше вимірювання. |
| `total` | Запит повністю: `dns + connect + tls + server + transfer`. Саме це число відчуває користувач. |

На що дивитись:

- великий `connect`/`tls` → проблема в мережевій відстані, а не в застосунку;
- великий `server` → повільний сам застосунок (або його БД/кеш);
- великий `transfer` → важкий payload або вузький канал, а не повільний сервер.

### Перцентилі

Кожен виміряний запит (типово 20; 3 прогрівочні запити не рахуються)
потрапляє в статистику. Невдалі запити виключаються з фаз, але їх видно в
`statuses` та у частці успіхів.

- **p50** (медіана) — половина запитів була швидшою. «Типовий» запит.
- **p95** — 95% запитів були швидшими, найповільніші 5% — повільнішими. Це
  хвіст: пороги та SLA порівнюйте з p95, а не з p50. p90/p99 є у JSON-виводі.
- **max** — найгірший одиничний запит серії.
- **mean** — показується приглушено й не випадково: середнє ховає хвіст, тож
  довіряйте спершу перцентилям.

Перцентилі рахуються методом найближчого рангу, без інтерполяції: p50 двох
вимірювань — це менше значення, а не вигадана середина. Якщо успішних запитів
менше ніж 10, скрипт попереджає, що перцентилі нерепрезентативні.

### Server-Timing

Якщо сервер віддає заголовок `Server-Timing` (специфікація W3C), його метрики
друкуються окремим рядком. Це *власний* внутрішній таймінг сервера —
чесніший за фазу `server`, у яку завжди входить мережевий раунд-трип.

## Опціональний бекенд pycurl

Стандартний бекенд використовує stdlib (`socket`/`ssl`/`http.client`). Для
байт-в-байт звірки з `curl` можна встановити `pycurl` вручну:

```bash
pip install pycurl
```

`pycurl` навмисно **не** входить у `requirements.txt` — PyShell ставить усі
залежності з цього файлу при кожному Prepare Env, а pycurl потребує системні
бібліотеки libcurl і може не зібнатись на деяких платформах. Прапорець
`--backend pycurl` з'явиться в v2.
