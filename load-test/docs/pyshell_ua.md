# Навантажувальний тест

Фазове навантаження на **сайт, яким ви володієте**, зі заданою вами
швидкістю — з живим графіком латентності/пропускної здатності та
звітом про деградацію відносно базової лінії. Єдиний свідомий виняток
колекції з пасивної філософії — і тому єдиний скрипт із контрактом.

> **Контракт володіння:** без підтвердження *I own this target* ран
> відмовляється стартувати. Навантаження на сайт, яким ви не
> керуєте, — це атака, якою б не була мотивація. Навіть на власному
> сайті скажіть хостеру/CDN, що ви робите — справжній load test
> зовні виглядає точно як маленький DDoS.

---

## Перед запуском

1. **Target URL** — сайт, який ви зараз навантажите. Трафік отримує
   лише цей хост.
2. Позначте **I own this target or have permission to load-test it**.
3. Оберіть фази, швидкість і тривалість, натисніть **Run** (⌘↩).

Pre-flight GET перевіряє, що ціль відповідає (і ще не 5xx-ить), перед
тим як згенеровано хоч один запит навантаження.

## Поля

### Target

- **Target URL** — схема + хост.
- **I own this target** — контракт; без нього ран відмовляється.

### Plan

- **Phases** — повторювані:
  - **Baseline** — GET-и головної; базова лінія, з якою порівнюють
    усі інші фази. Включайте її, якщо хочете пороги.
  - **Search** — `/?s=<випадковий термін>` на запит — обходить кеш,
    дістається до бази.
  - **REST API** — `/wp-json/wp/v2/posts`.
  - **Login page** — GET `wp-login.php`; ніколи не сабмітиться,
    креденшели не надсилаються.
  - **XML-RPC** — один мінімальний POST `system.listMethods` на
    запит; без ампліфікаційних пейлоадів.
  - **Custom paths** — ваші шляхи, round-robin (задайте їх у полі
    Custom paths).
- **Custom paths** — один шлях на рядок, починаючи з `/`.

### Load

- **Target rate (req/s)** — 1–100, стабільно тримається пейсером.
  Цільова швидкість — це стеля: досягнута (звітується по фазах) може
  лише відставати — воркери або сайт не встигають.
- **Phase duration (s)** — 5–300 на фазу; весь план має вкластись у
  1500 с (таймаут манифесту має запас).
- **Per-request timeout (s)** — запит повільніший за це рахується
  помилкою, а не латентністю.

---

## Результат

- **Results tab** — живий графік упродовж рана (середня латентність
  за секунду + запитів за секунду; вікно 120 секунд на довгих ранах),
  потім таблиця по фазах і звіт про деградацію:
  - **p95 понад 3× базового p95** → позначено;
  - **частка помилок понад 5%** → позначено;
  - без фази baseline у плані → числа стоять самі, без порогів (про
    це сказано, не сховано).
- **Артефакти** — `loadtest_results.json` (кожен запит з латентністю
  і статусом), `report.md`.

### Чесне читання

- Досягнута RPS нижча за цільову = сайт (або воркери) наситились —
  ця точка насичення і є знахідкою.
- Відповіді 429/503 — це захист сайта скидає навантаження — *здорова*
  відповідь під потопом, видна в колонці помилок.
  До/після зміни кешування — уся суть: міряйте [Server
  Timing](../../server-timing) без навантаження, навантажуйте тут,
  виправляйте, повторюйте. Яким навантаження виглядає з боку сайта —
  територія [Log Attack Checker](../../log-attack-checker).

## Коди виходу

- `0` — план виконано; позначки деградації — знахідки.
- `1` — ціль не відповіла, або вже 5xx-ить.
- `2` — неправильні аргументи (без підтвердження володіння, план понад
  лімітом, невідомі фази, custom без шляхів).
